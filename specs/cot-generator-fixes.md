## Fix 1 — Honest follow-up reasoning (no oracle values in `digit_mapping_analysis_follow_up_N`)

**Status:** Done — implemented in `src/cot_generator_v2/`

### Problem

`tells.py::_algebraic_tell()` currently uses the known solution as an oracle to
populate the follow-up text. Concretely:

- Branch 2 (result-position tell): computes `Lc, Rc` from `solution` and
  writes *"the result should be \<value\>"* — a value the LLM cannot derive at
  inference time.
- Branch 3 (operand-gap tell): computes `req = Lc` or `req = Rc` from
  `solution` and writes *"the left operand must be \<value\> (A=x, B=y)"* —
  again, oracle knowledge presented as deduction.

This is circular: the training text makes statements that require knowing the
answer in advance, so the model learns to produce confident conclusions it has
no legitimate way to reach.

### Fix

Replace oracle-derived values with observations derivable purely from the
**broken mapping's forward checks**, and frame the specific fix as a
**suggestion** rather than a certainty.

**New flow inside `make_tell`:**

1. **Private equation selection** (never in CoT): compare
   `solution_results` vs `broken_results` to identify which example equations
   newly broke after the perturbation. These are the equations to reason about.
   This comparison uses the solution, but only as a selector — no values from
   it enter the generated text.

2. **Observation from broken checks only**: for each newly-broken equation,
   describe what the forward check actually produced under the broken mapping:
   - which operands were decoded and to what values
   - what the operation computed
   - what the rhs target is
   - the size/direction of the gap

3. **Candidate reasoning**: from the structure of the failing equation (which
   positions the fix symbols occupy — operand left, operand right, result),
   reason about which symbol(s) are plausible causes of the mismatch. No
   oracle values; only what is observable.

4. **Framed suggestion**: name the specific fix (derived from the solution, via
   `_fix_change_phrase`) but frame it as a hypothesis:
   *"one viable option would be to swap A ↔ B"* rather than
   *"A and B must be swapped"*.

### Example contrast

**Before (oracle-dependent):**
> eq[1] (AB + C = X) still fails: with add (offset +0), the operands decode to
> 21 and 3 giving 24, but the rhs needs 15. eq[1]'s other symbols are already
> pinned … the left operand must be 12 (A=1, B=2). Minimal fix: swap A <-> B.

**After (honest forward-check):**
> eq[1] (AB + C = X) fails: with add, AB decodes to 21 and C to 3, giving 24,
> but the rhs target is 15. The gap of 9 points at the left operand; A and B
> are the symbols there. One viable option is to swap A ↔ B and see if that
> closes the gap.

### Files affected

- `src/cot_generator/tells.py` — rewrite `_algebraic_tell()` and `make_tell()`

## Fix 2 — Allow swaps involving question-only symbols

**Status:** Done — implemented in `src/cot_generator_v2/`

### Problem

`perturbation.py::build_chain()` restricts the swap pool to `eq_syms` — symbols
that appear in at least one example equation (line 103):

```python
eq_syms = [s for s in content_syms if any(s in es for es in eq_sets)]
```

This means a symbol that appears **only** in the question LHS is never a
candidate for any perturbation. Its digit is assigned in `digit_mapping_1` and
never challenged. The LLM never sees reasoning about why that symbol holds its
particular digit — the assignment is silent and unexplained.

### Fix

Relax the eligibility rule: **a perturbation is valid if it breaks at least one
example equation**, regardless of whether both symbols in the swap appear in
examples. The existing `_break_fails()` check already enforces this — no
additional gate is needed.

Concretely, for swaps allow `b` to be a question-only symbol as long as `a` is
in at least one example equation. The swap changes `a`'s digit (which affects
example equations) and `b`'s digit (which does not affect example equations
directly). `_break_fails()` will accept the pair only if `a`'s new digit
actually breaks some example equation.

**Change in `build_chain`:** build two pools —
- `eq_syms`: symbols in example equations (must be `a`, the first member)
- `all_syms`: all content symbols including question-only (can be `b`, the
  second member)

Reassigns are unchanged — they only move one symbol onto a spare digit, and
that symbol must be in an example to produce a meaningful tell.

### Why the follow-up still works (with Fix 1)

With Fix 1's honest approach, the follow-up is generated by:
1. Finding newly-broken equations (those containing `a`, the example symbol)
2. Describing the failure from the broken mapping's forward checks
3. Naming the fix as a suggestion: *"one viable option is to swap A ↔ Q"*

The question-only symbol `Q` appears in the suggestion because the fix is
known, but the reasoning leading to it is grounded in the example equations
that contain `A`. At inference time, the LLM's reasoning path would be: *"A's
digit seems wrong given the failing equations; swapping it with Q (which holds
A's correct digit) is a viable option because the bijection constraint means
only one symbol can hold each digit."*

### Files affected

- `src/cot_generator/perturbation.py` — relax `eq_syms` pool in `build_chain()`;
  split into `eq_syms` (first member) and `all_syms` (second member) for swaps

## Fix 3 — Motivated first digit mapping via constraint propagation (revised)

**Status:** Done — implemented in `src/cot_generator_v2/`

### Problem (original)

`_render_mapping_first()` in `render.py` listed digit assignments in priority
order with no justification. Digits were drawn from the final solution (oracle)
and `<digit_mapping_1>` showed the correct solution while its own follow-up
block analysed a *different, broken first-attempt mapping* — a mismatch.

### Goal (revised, June 2026)

Replace the priority-list with a **fully narrated constraint-derivation** that:
1. Derives per-equation and global allowed digit ranges per symbol
2. Applies forced-value propagation (bijection propagation across symbols)
3. Sorts symbols by `len(allowed[s])` ascending (fewest-options first, stable)
4. Picks in that fixed order with progressive pool reduction, explaining
   when a symbol becomes forced because prior picks consumed alternatives
5. Uses `chain.steps[0].mapping` (the first broken attempt) as the oracle,
   so `<digit_mapping_1>` matches exactly what `digit_mapping_analysis_1`
   and `…follow_up_1` analyse — the mismatch is fixed
6. Each subsequent block (`digit_mapping_2…N`) shows per-symbol allowed sets
   progressively narrowed by removing digits proved infeasible in the previous
   follow-up

### Step 1 — Build the allowed-range table

**Inputs:** example equations, operator candidate families per operator symbol
(from `analyze_operators()`), base.

**For each example equation `eq[i]`** with operator `op_j` having surviving
candidate operations `C_1 ... C_m`:

For each symbol `S` that appears in `eq[i]`:
```
allowed(S, eq[i]) = UNION over C in {C_1,...,C_m} of
    { d ∈ 0..base-1 | ∃ assignment of all other symbols in eq[i]
      such that C evaluates correctly on eq[i] with S=d }
```

This is computed by enumerating joint assignments of all symbols in `eq[i]`
(brute-force over `base^(k-1)` where k = number of distinct symbols in
`eq[i]`; for base=10 and k≤6 this is at most 100,000 iterations — fast).
The enumeration already handles cross-symbol coupling within the equation
(a symbol appearing in multiple positions is treated as one variable, not
independent positions).

**Intersect across equations** to get the per-symbol allowed range:
```
allowed(S) = INTERSECTION over eq[i] containing S of allowed(S, eq[i])
```

Symbols that appear only in the question LHS (not in any example) start
with `allowed(S) = {0,...,base-1}` (no constraint from examples).

**Output:** a dict `allowed: symbol -> set[int]`, and a per-equation table
`eq_allowed: (symbol, eq_index) -> set[int]` for narrative rendering.

### Step 2 — Pre-picking propagation pass

Before picking any symbol, sweep for forced values and propagate them:

```
changed = True
while changed:
    changed = False
    for each symbol S with |allowed(S)| == 1:
        d = the single element of allowed(S)
        for each equation E containing S:
            substitute S=d into E's constraint
            for each other symbol T in E:
                new_range = { t ∈ allowed(T) | ∃ valid completion of E with T=t, S=d }
                if new_range ⊂ allowed(T):
                    allowed(T) = new_range
                    changed = True
```

This propagates forced values across equations before any explicit pick is
made, catching chains of forced assignments without explicit enumeration.

### Step 3 — Symbol ordering and picking

Symbols are pre-sorted by `len(allowed[s])` ascending (stable: ties preserve
first-appearance order). This is `order_by_allowed(allowed, constrained_syms, base)`
in `digit_constraint.py`.

Picking then iterates this **fixed** order (not dynamic MRV re-selection):

```
order = sorted(constrained_syms, key=lambda s: len(allowed[s]))
pool = set(range(base))
for S in order:
    candidates = allowed[S] ∩ pool
    consumed   = allowed[S] − pool    # taken by prior picks

    if |candidates| == 0:  # contradiction fallback
        candidates = [oracle[S]]

    d = oracle[S]  # private selector — never printed
    if d not in candidates: d = candidates[0]

    case = 'forced'      if |allowed[S]| == 1           else
           'pool_forced' if |candidates| == 1            else
           'free'        (multiple candidates remain)

    record pick: (S, d, allowed_orig=allowed[S], candidates, consumed, case)
    pool.discard(d)
```

`oracle` is `chain.steps[0].mapping` (the first broken attempt) — not `solution`.
`consumed` drives the compact picking narrative (see Step 4 below).

### Step 4 — Narrative: `render_first_mapping_block`

The full content of `<digit_mapping_1>` is produced by
`render_first_mapping_block(examples, allowed_pre, allowed, eq_allowed, order, picks, base,
                            analyses, mode)`
in `digit_constraint.py`:

1. **Analysis bullets** — `_derive_constraint_observations` emits ~3–6 "reason → conclusion"
   bullets before the table:
   - **No-leading-zero**: for each symbol that is the MSD of a multi-distinct-symbol operand
     and has 0 excluded (without an additional operator upper bound), group into one bullet.
   - **Operator upper-bound**: for each equation where a symbol's `eq_allowed` has
     `len(aset) ≤ base - 2`, attribute to the equation's surviving candidate families.
     Uses `_fmt_explicit` so gaps are visible.
   - **Unconstrained**: closing bullet listing symbols whose final `allowed_pre` is the
     full digit range.
2. **Range table** — `eq_allowed[(s, eq_index)]` per cell, range form for large sets,
   `*` = unconstrained, `—` = not in equation. Final `allowed` column uses
   `_fmt_allowed_column` (shows `{0..N-1}` instead of `*` for the full set).
3. **Propagation** — emitted **only** when a forced singleton actually removes digits
   from other symbols (no "no propagation needed" fallback line).
4. **Picking** — lead-in `"Picking from the initial pool {0,1,…}, starting with
   the symbol that has the fewest allowed options:"` followed by numbered lines:
   - no consumed digits → `N. s → allowed: {set} → pick randomly d → pool → {after}`
   - consumed digits present → `N. s → reduce {consumed} from allowed {set} → pick randomly d → pool → {after}`
   - Pool after each pick always explicit (`_fmt_explicit`).
5. **Resulting assignment** list.

### Step 5 — Progressive narrowing in chain blocks (`_render_mapping_next`)

After each follow-up identifies infeasible digits, `reduce_allowed_from_followup`
removes `step.mapping[s]` for each fix symbol `s` from `running_allowed`. The
next `_render_mapping_next` shows:
- Lead-in: "Previous analysis ruled out: s ≠ d, ...  Let's try ..."
- Per-symbol listing with explicit current `running_allowed[s]` (shows the hole).

### Interaction with the perturbation chain

`chain` is built **before** picks so the oracle is `chain.steps[0].mapping`.
This ensures `<digit_mapping_1>` displays the first broken attempt — exactly
what `digit_mapping_analysis_1` and `…follow_up_1` analyse. Nothing in chain
construction changes.

### Files affected

- `src/cot_generator_v2/digit_constraint.py` — public API:
  `build_allowed_table`, `propagate`, `order_by_allowed`, `picking_sequence`,
  `render_first_mapping_block` (now takes `analyses` + `mode` args), `reduce_allowed_from_followup`.
  New private helpers: `_fmt_allowed_column`, `_msd_of_operand`, `_derive_constraint_observations`.
- `src/cot_generator_v2/render.py` — passes `analyses` and `mode` to `render_first_mapping_block`.
  Chain built before picks; progressive `running_allowed` maintained across chain loop;
  `_render_mapping_next` enhanced with `running_allowed` + `just_removed` args.
- `src/cot_generator_v2/perturbation.py` — swap partner `b` now restricted to `eq_syms`
  (example-visible symbols only), closing the dormant Fix 2 visibility leak.
- `digit_priority.py` — no longer called from the v2 arithmetic CoT path.

## Fix 4 — Unified CoT structure: concat-check first, arithmetic second

**Status:** Done — implemented in `src/cot_generator_v2/`

### Problem

The current implementation has two completely separate CoT pipelines:
- `render_concat_cot()` — short CoT for pure-concat puzzles (no digit mapping)
- `render_cot()` — full arithmetic CoT with digit mapping and perturbation chain

The model sees two structurally unrelated CoT shapes for the same input
format. There is no shared reasoning between them, and the arithmetic CoT
starts abruptly with operator candidate analysis without first ruling out
the simpler explanation.

### Goal

Unify both pipelines under a single CoT shape that **always tries the easy
concatenation pattern first**, then either terminates (concat found) or
transitions into the arithmetic path (concat ruled out). The transition from
concat failure into arithmetic reasoning is now explicitly motivated.

### New unified structure

```
<initial_reasoning>
    Problem statement, labeled equation list, operand/operator symbols.
    Shorter than the current version — std/le encoding details are deferred
    to the arithmetic path and not shown if concat succeeds.
</initial_reasoning>

<concat_check>
    Attempt forward and reverse concatenation on all equations that share
    the same operator symbol as the question LHS.

    OUTCOME A (all equations pass — pure concat):
        State the direction (forward/reverse), verify each equation briefly,
        conclude the rule applies. CoT ends here.

    OUTCOME B (any equation fails — concat ruled out):
        State which equation failed and why (the rhs does not match the
        operand symbols in either order). Conclude concat does not apply
        for this operator and the puzzle requires a hidden digit mapping.
</concat_check>

--- CoT ends here for pure-concat puzzles ---

<available_operations>         (arithmetic path only)

<operator_N_candidates>        (one block per operator symbol)
<factual_observations_operator_N>

<digit_range_table>            (Fix 3 — replaces digit_priority)

<digit_mapping_N>              (one block per attempt)
<digit_mapping_analysis_N>
<digit_mapping_analysis_follow_up_N>

<conclusion>
```

### Check logic for `<concat_check>`

Only equations whose operator symbol matches the **question LHS operator**
are relevant. Other operators are irrelevant to whether the question's
operator is concat.

```
relevant = [E for E in examples if E.op == question.op]
for E in relevant:
    check forward:  rhs == l0 l1 r0 r1 ?
    check reverse:  rhs == r0 r1 l0 l1 ?
    if neither holds:
        STOP — record E as the failing equation, conclude concat ruled out
if all relevant pass:
    record the direction, derive the answer, done
```

One failing equation is sufficient to rule out concat — stop immediately
and do not check remaining equations. This keeps `<concat_check>` concise
for arithmetic puzzles (it always terminates at the first failing equation).

### Wording guidelines

**`<initial_reasoning>`** — shorter than current. Remove the lengthy
preamble about std/le encoding (move that to the arithmetic path, after
concat fails). Keep: problem statement, equation list with labels eq[1]…,
operand symbols, operator symbols.

**`<concat_check>` — concat passes (pure concat):**
```
Let's first check if the operator simply concatenates operand symbols.
Equations sharing operator `+` with the question: eq[1], eq[2], eq[3].

- eq[1]: AB + CD = ABCD → forward concat ✓
- eq[2]: AB + CD = ABCD → forward concat ✓
- eq[3]: AB + CD = ABCD → forward concat ✓

All relevant equations satisfy forward concatenation. The rule applies
directly — no digit mapping needed.
```

**`<concat_check>` — concat fails (arithmetic path):**
```
Let's first check if the operator simply concatenates operand symbols.
Equations sharing operator `+` with the question: eq[1], eq[2].

- eq[1]: AB + CD = ABCD → forward concat ✓
- eq[2]: >#+>| = #% → rhs is #% which is neither >#+>| nor |>+#>.
  Forward and reverse concat both fail. ✗

Concat does not apply. The puzzle requires a hidden transformation rule:
a digit mapping, an operator mapping, and a magnitude encoding strategy.
```

### What changes in the code

**`src/cot_generator/render.py`**

- Extract a new `_render_initial_reasoning()` (shorter version, no std/le
  detail) and `_render_concat_check(examples, q) -> (str, str | None)`
  where the second return value is the concat family if found, else `None`.
- `render_concat_cot()`: call `_render_initial_reasoning()` +
  `_render_concat_check()` (outcome A), then `<conclusion>`. Retire the
  current separate initial reasoning block inside `render_concat_cot`.
- `render_cot()`: call `_render_initial_reasoning()` +
  `_render_concat_check()` (outcome B, which always fires for arithmetic
  puzzles), then continue with `<available_operations>` onwards. The
  outcome B text explicitly introduces the need for a digit mapping,
  replacing the current abrupt start of the operator analysis.

**`src/cot_generator/decode.py`**

- `detect_pure_concat()` already performs the check programmatically.
  Add a companion `render_concat_check_block(examples, q, fam | None)`
  that produces the `<concat_check>` inner text for both outcomes, reusing
  the same per-equation verification logic.

**`src/cot_generator/generate.py`**

- No change to routing logic — `_is_feasible()` still separates arithmetic
  from concat rows. The difference is only in what the rendered text looks
  like, not in which renderer is called.

### Files affected

- `src/cot_generator/render.py` — refactor `render_concat_cot()` and
  `render_cot()` to share `_render_initial_reasoning()` and
  `_render_concat_check()`
- `src/cot_generator/decode.py` — add `render_concat_check_block()`

## Fix 5 — Early-stop rules during digit-mapping analysis

**Status:** Done — implemented in `src/cot_generator_v2/`

### Motivation

The `<digit_mapping_analysis_N>` blocks currently check all operators against
all equations exhaustively, even when the outcome is already determined.
This mirrors the concat check's stop rule (one failure stops immediately)
applied to the operator candidate analysis after each digit mapping.

All stop rules below are **implementation-level decisions** — the code uses
oracle knowledge (`ops_mapping`) to decide when to stop programmatically,
but the generated CoT text never references "the expected program" or "the
solution." The text only reports what the analysis observes (candidates
surviving or being eliminated) as if discovering the program for the first time.

---

### Stop Rule 2a — First operator loses all candidates → mapping infeasible, stop

**Trigger:** any operator's surviving candidate set becomes empty after
checking an equation.

**Action:** stop the analysis immediately. Do not check remaining operators
or equations. State which operator lost all candidates and which equation
caused it.

**Text pattern:**
```
Checking operator `+` under mapping_1:
- add(21, 34) = 55, rhs target = 46 ✗
- mul(21, 34) = 714 ✗
- absdiff(21, 34) = 13 ✗
No candidate survives for `+` on eq[1]. This mapping is infeasible.
```

This is the **direct analogue of the concat stop rule** and has the highest
impact: failing attempts produce very short analysis blocks instead of
exhaustively checking all operators.

---

### Stop Rule 2b — Operator reduced to one candidate → lock in, carry forward

**Trigger:** after checking one or more equations for an operator, exactly
one candidate (family + offset + mode) survives.

**Action:** mark the operator as determined. Stop checking further equations
for it. Use the locked-in candidate as a constraint when checking other
operators (a symbol that appears in equations for multiple operators now has
a known operation applied to it).

**Text pattern:**
```
After eq[1]: only add (offset 0, standard) survives for `+`.
Operator `+` determined. Carrying forward.
```

---

### Stop Rule 2c — All operators determined → verify or continue

**Trigger:** every operator has exactly one surviving candidate.

This rule has two branches depending on whether the determined program
matches the solver's anchored program (`ops_mapping`). The code checks this
internally but the text never exposes it.

**Branch A — determined program IS the anchored program:**

Stop immediately. All equations for these operators have been satisfied by
this program (the solver guarantees it exists). State the determined program
and conclude the mapping is feasible.

**Text pattern:**
```
All operators are now determined:
- `+` → add (offset 0, standard)
- `^` → mul (offset 0, standard)
All checked equations pass. This mapping yields a feasible program.
```

**Branch B — determined program is NOT the anchored program:**

Do NOT stop. A different feasible program has been found from the equations
checked so far, but it may be eliminated by the remaining unchecked equations.
Continue checking. Do not mention in the text that this is a "different"
program — just continue the analysis naturally.

**Text pattern (continuing):**
```
After eq[2]: all operators appear determined. Checking eq[3] to confirm
this program holds across all equations...
- eq[3]: add(12, 34) = 46, rhs = 46 ✓
- eq[3]: also consistent under the previous candidate. Checking eq[4]...
- eq[4]: add(21, 43) = 64, rhs = 57 ✗ — this candidate is eliminated.
Remaining candidate for `+`: mul. Continuing.
```

The text presents this as natural discovery — an earlier determination that
turns out to be provisional, revised as more equations are checked.

---

### Stop Rule 3 — Encoding mode determined → lock in, stop testing the other

**Trigger:** after checking one or more equations, only one encoding mode
(standard or little_endian) is consistent across all operators.

**Action:** lock the mode and stop testing the eliminated mode for all
subsequent equation checks.

**Text pattern:**
```
eq[1] rules out little_endian for all operators. Encoding fixed to standard.
```

---

### Priority for implementation

| Rule | Impact | Analogy |
|---|---|---|
| 2a — first operator exhausted | **High** — failing attempts become short | Direct concat stop rule analogue |
| 2c-A — all determined, correct program | Medium — clean termination at solution step | Natural convergence |
| 2b — operator locked to one candidate | Medium — fewer redundant checks | Unit propagation |
| 2c-B — all determined, wrong program | Medium — avoids premature stop | Correctness guard |
| 3 — mode locked | Low — modes determined early anyway | Cross-operator propagation |

### Files affected

- `src/cot_generator/analysis.py` — add early-exit logic inside the
  per-operator, per-equation loop; expose `is_infeasible` and `is_feasible`
  flags on `AttemptAnalysis` so `render.py` can truncate the block text
  accordingly
- `src/cot_generator/render.py` — use the flags to stop appending analysis
  text once a stop rule fires

## Fix 6 — Correct offset handling: elimination across equations, not first-match lock-in

**Status:** Done — implemented in `src/cot_generator_v2/`

### Problem

The current `<available_operations>` block states:

> "Offset rule: start at offset 0; if a result is close to the target by a
> small constant in the allowed set, fix that offset and carry it forward
> for every later check of the same op."

This is incorrect. "Fix that offset" after the first passing equation is
premature — if multiple offsets satisfy the first equation, locking in the
first one found discards other valid offsets that may be the only ones
compatible with later equations.

### Correct semantics

The offset is a **global property of the program** — one fixed offset per
`(family, operator_symbol)` pair, shared across every equation that uses
that operator. It behaves identically to the family candidates: each
equation eliminates `(family, offset)` pairs that fail it, and only
survivors are carried forward.

```
initial candidates for `+`:
  { (add, -2), (add, -1), (add, 0), (add, +1), (add, +2),
    (mul, -2), ..., (mul, +2),
    (absdiff, -2), ..., (absdiff, +2),
    (gcd, 0), (lcm, 0), ...  ← offset-free families have only offset 0 }

after eq[1]: eliminate pairs where family(L, R) + offset ≠ target
after eq[2]: eliminate pairs where family(L, R) + offset ≠ target
...
→ exactly 1 pair survives: determined (stop rule 2b)
→ 0 pairs survive:        infeasible (stop rule 2a)
```

An offset that satisfies eq[1] **survives** eq[1] — it is not yet
**determined**. Determination happens only when exactly one `(family, offset)`
pair remains across all equations checked so far.

### Why "first match, lock in" usually works but is conceptually wrong

For base 10, operand values (0–99) and result sizes are tight enough that
typically only one offset satisfies the first equation. The approximation
holds in practice almost always. However:

- It is wrong in edge cases where two offsets both satisfy the first equation
  but only one satisfies later equations.
- It introduces a conceptual inconsistency: families and offsets are treated
  differently when they should follow the same elimination logic.
- The LLM learning from this CoT would learn a different rule for offsets
  than for families, when both are really the same kind of constraint.

### Updated offset rule wording (for `<available_operations>` block)

Replace current text with:

> "**Offset rule:** for operations with an offset parameter, each `(operation,
> offset)` pair is treated as a separate candidate. A pair survives an equation
> only if `operation(L, R) + offset = target`. Pairs that fail any equation are
> eliminated. Once a single pair remains it is locked in and carried forward.
> If no pair survives, the operation family is eliminated for this operator."

### Interaction with Fix 5 stop rules

No new stop rules are needed. The offset dimension is absorbed into the
existing `(family, offset)` candidate space — stop rules 2a and 2b apply
directly:

- **2a**: if all `(family, offset)` pairs for an operator are eliminated →
  infeasible, stop.
- **2b**: if exactly one `(family, offset)` pair survives → locked in,
  carry forward.

### Files affected

- `src/cot_generator/render.py` — update `_available_operations()` wording
- `src/cot_generator/analysis.py` — verify that the internal candidate
  tracking already treats `(family, offset)` pairs as the unit of
  elimination (not families alone); correct if not

## Fix 7 — Correct `<available_operations>` text and add result constraints

**Status:** Done — implemented in `src/cot_generator_v2/`

### Problem

`_available_operations()` in `render.py` has two issues:

1. **Wrong offset sets** for three families (the sets shown do not match
   `families.py`).
2. **Missing result constraints** — sign and guard conditions that allow the
   LLM to eliminate candidates structurally before any digit is tried.
3. **Old offset rule wording** — already addressed by Fix 6; included here
   for completeness of what changes in this function.

### Corrected operation list

Replace the current list with:

```
- add(a, b) = a + b + offset,        offset in {-1, 0, +1, +2}
- sub_signed(a, b) = a - b           result can be negative
- rsub_signed(a, b) = b - a          result can be negative
- mul(a, b) = a x b + offset,        offset in {-1, 0, +1}
- absdiff(a, b) = |a - b| + offset,  offset in {-2, -1, 0, +1},  result ≥ 0
- neg_absdiff(a, b) = -|a - b|       result always ≤ 0
- gcd(a, b) = gcd(a, b)
- lcm(a, b) = a x b // gcd(a, b)     if (a and b) else 0
- fdiv(a, b) = a // b                 if b != 0
- mod(a, b) = a % b                   if b != 0
- rmod(a, b) = b % a                  if a != 0
- concat_fwd(a, b) = a x 10^(digits of b) + b
- concat_rev(a, b) = b x 10^(digits of a) + a
```

**Offset corrections vs current text:**

| Family | Current (wrong) | Correct |
|---|---|---|
| `add` | {-2,-1,0,+1,+2} | **{-1, 0, +1, +2}** |
| `mul` | {-2,-1,0,+1,+2} | **{-1, 0, +1}** |
| `absdiff` | {-2,-1,0,+1,+2} | **{-2, -1, 0, +1}** |

**New constraints added:**

- `sub_signed`, `rsub_signed` → *result can be negative* (useful: if decoded
  RHS is unsigned, these can be structurally eliminated before digit mapping)
- `absdiff` → *result ≥ 0* (the negative-offset variants guard against
  producing a negative result; if `|a-b| + offset < 0` the guard fails)
- `neg_absdiff` → *result always ≤ 0* (if decoded RHS is positive this family
  is eliminated immediately)
- `rmod` → *if a != 0* (was missing; mirrors the `mod` and `fdiv` guards)

### What `feasibility.py` already handles (no code change needed there)

The structural filters in `feasibility.py` already act on these constraints
programmatically before digit mapping:

- **Sign check** (lines 147–178): if RHS is unsigned (all example rhs non-negative,
  L≠R), `neg_absdiff`, `sub_signed`, and `rsub_signed` are all dropped — `neg_absdiff`
  always ≤ 0; `sub_signed`/`rsub_signed` can go negative and their non-negative case
  is already covered by `absdiff` (protected gold-op families are exempt). If RHS is
  signed, only `sub_signed`, `rsub_signed`, `neg_absdiff` survive.
- **Concat structural check** (lines 187–254): symbol-identity check.
- **Magnitude bounds** (lines 263–312): lower and upper digit-count checks.
- **Self-application check** (lines 314–382): L==R cases for absdiff offsets,
  zero-on-equal families, fdiv→1, gcd/lcm→operand.

The guards for `rmod` (a≠0), `fdiv` (b≠0), `mod` (b≠0) are evaluation-time
guards — they cannot be checked structurally before digits are assigned. They
are already applied correctly in `analysis.py` via `apply_family()` returning
`None` on guard failure. **No change needed in `feasibility.py`.**

The fix is **text-only**: update `_available_operations()` in `render.py` so
the LLM reading the CoT sees the correct offsets and constraints.

## Fix 8 — Explicit zero-padding and sign reasoning in the conclusion

**Status:** Done — implemented in `src/cot_generator_v2/`

### Problem

Two encoding decisions are made silently in `_answer_working()` and
`predict_answer()` using oracle values the LLM cannot access at inference time:

1. **Zero-padding width** — `q.res_len` is parsed from the gold answer. The
   conclusion shows `encode: |value| -> digits -> answer` without explaining
   where the expected width came from.

2. **Sign position** — `q.sign_pos` (prefix / postfix) is read from the gold
   answer format. The conclusion never explains why a sign is appended or
   where it goes.

At inference time the LLM must infer both from the example equations.
The conclusion currently reads as oracle-confident; it should instead show
the observation from examples that grounds each decision.

### Fix: add an answer-format observation block before the encode step

Insert a short `<answer_format>` block (or inline paragraph) just before the
encode step in the conclusion. It contains:

#### Part 1 — Width / zero-padding

Scan example equations whose operator == question operator. Report the
observed answer widths and use them to justify the padding.

**Case A — examples exist and widths are consistent:**
```
Observing the answer format from the examples using operator `+`:
- eq[1]: rhs has 2 symbols → answer width = 2
- eq[2]: rhs has 2 symbols → answer width = 2
All examples agree: answer width is 2. Zero-pad the result to 2 digits if needed.
```

**Case B — examples exist but widths vary:**
```
Observing the answer format from the examples using operator `+`:
- eq[1]: rhs has 2 symbols
- eq[3]: rhs has 3 symbols
Widths vary across examples. Using the width from the question answer field (2).
```

**Case C — no example uses the question operator:**
```
No example equation uses operator `+`, so the answer width cannot be observed.
Using the width from the question answer field (2) as a best guess.
```

#### Part 2 — Sign

Only shown when the determined operation family can produce a negative result
(`sub_signed`, `rsub_signed`, `neg_absdiff`).

Scan example equations for the question operator whose rhs carries a sign
(`has_sign = True`). Report the observed position and use it to justify the
sign convention.

**Case A — example(s) show a signed result:**
```
Observing sign convention from the examples using operator `+`:
- eq[3]: result is negative; sign appears as postfix (operator glyph after
  the magnitude, e.g. `35+`).
Applying postfix sign convention to the answer.
```

**Case B — no example shows a signed result, but family can be negative:**
```
No example with operator `+` shows a signed result, so the sign position
cannot be observed. If the result is negative, guessing postfix convention
(operator glyph appended after the magnitude).
```

**Case C — family is always non-negative (add, mul, absdiff, etc.):**
No sign block shown — the operation cannot produce a negative result, so
zero-padding alone is sufficient.

### Where to insert

Inside `_answer_working()` in `render.py`, between the "apply" line and the
"encode" line. The encode line already shows the padded digits and final
symbol string — the new block just explains the decisions that produced them.

**New structure of the encode section:**

```
- apply:  add(12, 34) = 46
- answer format: all examples with `+` show 2-symbol answers → width = 2;
  result 46 fits in 2 digits, no padding needed.
- encode: 46 → digits 4,6 → XY
```

Or with padding:

```
- apply:  add(3, 4) = 7
- answer format: all examples with `+` show 2-symbol answers → width = 2;
  result 7 is 1 digit, zero-pad to 2 → 0,7
- encode: 07 → digits 0,7 → ZX
```

Or with sign:

```
- apply:  sub_signed(12, 34) = -22
- answer format: eq[2] shows postfix sign for operator `+`; result is negative.
- sign: appending `+` after magnitude → 22+
- encode: 22 → digits 2,2 → XY → XY+
```

## Fix 9 — Budget framing, running best-candidate `\boxed{}`, minimal tags, n-shot rounds

**Status:** Done — implemented in `src/cot_generator_v2/`

### Motivation

During inference the model runs out of token budget before reaching
`<conclusion>`, producing no `\boxed{}` answer. The metric extracts the
**last** non-empty `\boxed{}` in the full text. Four coordinated changes
guarantee the model always emits an answer within budget.

---

### 9a — Budget framing at the start

Add one sentence to `<initial_reasoning>` (after the equation list):

> "We will attempt up to N digit mappings. After each attempt we record
> the current best candidate. If no fully feasible mapping is found within
> N attempts, we conclude with the best candidate found so far."

`N` is the configured perturbation rounds for this row (see §9d). This
conditions the model to expect a conclusion after a bounded number of steps.

---

### 9b — Running `\boxed{}` in every follow-up block

Append one line at the end of every `<digit_mapping_analysis_follow_up_N>`
block:

```
Current best candidate: \boxed{X}
```

where `X` is the answer computed from the current mapping (even if the
mapping is not fully feasible). Use `predict_answer()` with the current
step's digit mapping and the anchored program.

**Why this works with the metric:**

| Situation | Last `\boxed{}` seen | Metric result |
|---|---|---|
| Model reaches `<conclusion>` | Final verified answer | Correct |
| Budget runs out after follow-up N | Best candidate at step N | Best available guess |
| Budget runs out before first follow-up | `NOT_FOUND` | Wrong (unavoidable) |

The best-guess `\boxed{}` in each follow-up acts as a safety net. The final
`<conclusion>` always overrides it if the model reaches it.

**Wording note:** frame the intermediate `\boxed{}` as a candidate, not a
certainty:

```
This mapping does not fully satisfy all equations yet.
Current best candidate: \boxed{46}
```

For the solution step (last mapping):

```
All equations satisfied. Answer confirmed: \boxed{46}
```

---

### 9c — Minimal delimiter tags

Remove structural tags that cost tokens but are not needed by the metric
or by the model's core reasoning:

**Remove:**
- `<initial_reasoning>` / `</initial_reasoning>`
- `<available_operations>` / `</available_operations>`
- `<operator_N_candidates>` / `</operator_N_candidates>`
- `<factual_observations_operator_N>` / `</factual_observations_operator_N>`
- `<digit_priority>` / `</digit_priority>`
- `<digit_range_table>` / `</digit_range_table>`
- `<concat_check>` / `</concat_check>`
- `<concat_evidence>` / `</concat_evidence>`

**Keep:**
- `<digit_mapping_N>` / `</digit_mapping_N>` — anchors attempt numbering
- `<digit_mapping_analysis_N>` / `</digit_mapping_analysis_N>` — anchors analysis per attempt
- `<digit_mapping_analysis_follow_up_N>` / `</digit_mapping_analysis_follow_up_N>` — anchors follow-up + running `\boxed{}`
- `<conclusion>` / `</conclusion>` — critical: model must learn to open and close this to emit the final `\boxed{}`

The kept tags provide enough structure for the model to track which attempt
it is on and where the final answer lives. The removed tags are scaffolding
useful for human reading but wasteful during training.

---

### 9d — n-shot-based perturbation rounds

Replace the global `cfg.perturbation_rounds` with a per-row value derived
from `dataset_category`. Training covers only 3-, 4-, and 5-example puzzles.

```python
_ROUNDS_BY_CATEGORY = {
    "examples_3": 1,
    "examples_4": 2,
    "examples_5": 3,
}

def perturbation_rounds_for_row(row: dict, cfg: CotGeneratorConfig) -> int:
    cat = str(row.get("dataset_category", ""))
    return _ROUNDS_BY_CATEGORY.get(cat, cfg.perturbation_rounds)
```

**Rationale:** more examples = more equations available to ground perturbation
follow-ups. With 3 examples, finding 2+ disjoint valid breaks that produce
grounded tells is already hard. The mapping `n_examples - 2` is conservative
and avoids the perturbation chain silently capping below the request.

The existing token-cap retry loop in `generate.py` already shrinks rounds
further if the CoT exceeds `max_cot_tokens`, so this sets the per-row
ceiling only.

---

### Files affected

- `src/cot_generator/render.py` — §9a: add budget sentence to
  `_initial_reasoning()`; §9b: extend follow-up rendering to append
  `\boxed{}`; §9c: remove tag wrappers for dropped sections
- `src/cot_generator/generate.py` — §9d: call
  `perturbation_rounds_for_row()` instead of using `cfg.perturbation_rounds`
  directly
- `src/cot_generator/config.py` — §9d: `perturbation_rounds` becomes a
  fallback default only (used when `dataset_category` is absent)

## Augmentation 1 — Perturbation-order variations as additional training samples

**Status:** Done — implemented in `src/cot_generator_v2/`

### Insight

Given k disjoint breaks, the most-broken starting mapping `mapping_1` is
identical regardless of the order in which the breaks are applied (disjoint
dict updates commute). However, **every intermediate mapping differs across
orderings**. For k breaks there are k! distinct orderings, each producing a
genuinely different reasoning chain:

- Different intermediate digit mappings at each step
- Different equations failing at each step → different analysis blocks
- Different follow-up reasoning at each step

All orderings are valid: they all start from the same `mapping_1`, fix one
break per step, and converge to the same solution.

Currently `build_chain` picks exactly one ordering — coupling-sorted
descending (messiest break first). The remaining k!−1 orderings are discarded.

### Strategy

For each puzzle row that has k ≥ 2 perturbations, generate additional CoT
traces by re-running `render_cot` with different break orderings. Each
ordering becomes a **new row** appended to the output parquet — same puzzle
input (`prompt`, `answer`, `digits_mapping`, `ops_mapping`, etc.), different
`cot` text and `cot_num_perturbations` value.

**Ordering selection:** k! grows fast (k=4 → 24). Rather than exhausting all
permutations, sample a bounded number of orderings per puzzle (e.g.
`max_order_variants` config key, default 2–3). The coupling-sorted ordering
(current default) is always included as variant 0.

### Implementation sketch

1. After building the candidate break list in `build_chain`, expose the
   candidates before the coupling sort.
2. Add a `break_order: list[int]` parameter to `build_chain` that specifies
   the permutation to apply (indices into the candidate list). Default = current
   coupling-sorted order.
3. In `generate.py`, after generating the base CoT for a row, loop over
   additional orderings and call `render_cot` with each. Append each result as
   a new row in the output dataframe with the same source columns and a new
   `cot_variant_index` column (0 = base, 1..N = augmented variants).

### Output parquet impact

New rows are **appended**, not replacing existing ones. Each augmented row is
a copy of the source row's metadata columns plus the new CoT text. A
`cot_variant_index` column distinguishes base from augmented samples.

### Files affected

- `src/cot_generator/perturbation.py` — expose pre-sorted candidates; accept
  `break_order` parameter
- `src/cot_generator/render.py` — pass `break_order` through to `build_chain`
- `src/cot_generator/generate.py` — outer loop over orderings; append new rows
- `src/cot_generator/config.py` — add `max_order_variants: int` config key

## Augmentation 2 — Different solution tuples (GRPO phase only)

**Status:** Future proposal — do NOT use in SFT

### What this augmentation does

The solver can find multiple distinct solution tuples
`<digit_mapping, ops_mapping, solver_strategy>` for the same puzzle (rows with
`solution_id > 0` in the parquet already capture these). Each tuple produces a
different CoT with different intermediate programs and typically a different
`\box{}` answer.

Using these as additional training samples teaches the model that the puzzle is
genuinely underdetermined — multiple valid programs exist.

### Why this must NOT be used in SFT

SFT applies loss to the full CoT sequence. When the same prompt has two CoTs
with different programs, the model receives:

- **Conflicting gradient signal** on all intermediate tokens (digit values,
  operator choices, analysis text) — the two programs disagree here.
- **Consistent signal** on `\box{}` only when the two programs happen to
  produce the same final answer.

The worst case is **same answer, different program**: the consistent answer
signal masks the intermediate incoherence during training, and the model learns
to produce averaging artifacts (e.g. digit values that are neither program A
nor program B) that look plausible but are not valid solutions.

| Case | `\box{}` same? | Program same? | SFT risk |
|---|---|---|---|
| Augmentation 1 (order variation) | Yes | Yes | None |
| Augmentation 2, programs yield same answer | Yes | No | **High** — answer masks incoherence |
| Augmentation 2, programs yield different answer | No | No | Moderate |

### Why it is safe in the GRPO phase

GRPO uses the solver as a deterministic verifier: reward is granted only when
the extracted solution tuple is algebraically consistent with the puzzle
(see memory: GRPO solver reward). The intermediate CoT text is not directly
supervised — only the final answer and the tuple it encodes are scored.

Under GRPO, diverse programs for the same prompt are a **feature**:
- Different rollouts explore different valid programs.
- Each is rewarded independently if it leads to a consistent answer.
- The model learns that multiple reasoning paths are valid without receiving
  conflicting gradient signal on intermediate tokens.

### Implementation notes

- Source: rows with `solution_count > 1` in the existing parquet already
  provide different solution tuples at no extra solver cost. Check coverage
  before scheduling new solver runs.
- Each solution tuple row gets its own CoT generated by `render_cot` anchored
  to that tuple's `ops_mapping` + `digits_mapping`.
- Tag augmented rows with `cot_variant_source = "solution_tuple"` to allow
  filtering during the SFT stage (exclude) and GRPO stage (include).

### Files affected

- `src/cot_generator/generate.py` — process `solution_id > 0` rows and tag
  them with `cot_variant_source`
- `config.yaml` — add `include_multi_solution_variants: bool` flag (default
  `false`; enabled only for GRPO dataset generation)

## Augmentation 4 — Guess samples via chain truncation (`generate_guess_samples` flag)

**Status:** Done — implemented in `src/cot_generator_v2/`

### Motivation

Fix 9 guarantees the model emits intermediate `\boxed{}` candidates during full-solution CoTs. However, the model never sees a training example where `<conclusion>` itself says "budget exhausted — best guess: \boxed{X}". Without such examples the model may always try to write a confident conclusion even when all N attempts are spent and no feasible mapping was confirmed, producing hallucinated certainty at inference time.

This augmentation creates explicit samples for that case by truncating existing full-chain CoTs one step before the solution.

---

### New config field

Add to `CotGeneratorConfig`:

```python
generate_guess_samples: bool = False
```

YAML key: `generate_guess_samples: true/false` (under `cot_generator:`).

When `False` (default): existing behaviour — only full-solution CoTs are written.  
When `True`: for every full-chain row with `k ≥ 2` perturbation rounds, also attempt to produce a truncated guess-sample companion row.

---

### Generation procedure (per row, when enabled)

1. Build the full k-round CoT as normal. The last mapping is the solution.
2. Drop the last round (solution mapping + its analysis + its follow-up).
3. Compute `X = predict_answer(mapping_{k-1})` — the answer from the second-to-last mapping.
4. **Filter**: keep the truncated sample only if `X == gold_answer`.  
   *This condition holds when none of the symbols swapped in the final perturbation appear in the result variable. It is a minority of rows.*
5. Replace `<conclusion>` with a budget-exhausted block:
   ```
   <conclusion>
   Budget of N attempts used. No fully feasible mapping confirmed across all equations.
   Returning best candidate found: \boxed{X}
   </conclusion>
   ```
   The budget sentence mirrors the framing established in Fix 9a so the model sees a consistent pattern.
6. Write this truncated row alongside the full-solution row in the output parquet, tagged with `cot_variant_source = "guess_truncated"`.

---

### What to do with rows that fail the filter

Truncated rows where `X != gold_answer` are **not** safe for SFT (they train on `\boxed{wrong}`). They should be:
- Silently skipped if the pipeline target is SFT only.
- Optionally kept in a separate parquet tagged `cot_variant_source = "guess_truncated_grpo_only"` for the GRPO phase, where the verifier reward handles wrong answers correctly.

---

### Volume guidance

Aim for 10–15% of the final training set as guess samples. Above that, the model becomes over-reluctant to commit to a confident conclusion when it actually could. Enforce this cap by sampling from the surviving (filtered) truncated rows after generation rather than including all of them.

---

### Files affected

- `src/cot_generator/config.py` — add `generate_guess_samples: bool = False` field and YAML loader key
- `src/cot_generator/generate.py` — after writing each full-solution row, conditionally build and filter the truncated companion (gated on `cfg.generate_guess_samples`)
- `src/cot_generator/render.py` — add `render_guess_conclusion(mapping, gold_answer, attempts_used)` that emits the budget-exhausted `<conclusion>` block

## Fix 10 — Honest unconstrained-symbol handling throughout the CoT

**Status:** Done — implemented in `src/cot_generator_v2/render.py`

### Problem

Three places leaked oracle knowledge about symbols the examples never constrain:

1. **Header** (`_render_initial_reasoning`): "Operand symbols:" listed every
   content symbol via `content_symbols(examples + [q])`, including symbols that
   appear only in the answer (e.g. `@`, `'`) and question operands the examples
   never constrain (e.g. `|`). The reasoner cannot observe these.
2. **Digit-mapping derivation** (priority table, range table, picking narrative,
   perturbation chain, conclusion digit listing): included unconstrained symbols
   because `operand_syms = content_symbols(examples + [q])` was passed to
   `compute_digit_priority` and `build_chain`.
3. **Conclusion `_answer_working`**: the decode line showed exact integer values
   for operands whose symbols were never seen in examples; the encode line
   re-mapped result digits to symbols without acknowledging the guess; the caveat
   was in the wrong direction (symbol→digit).

### Decision

- **Option C** — keep the symbol answer unchanged; add honest narrative.
- **Scope B** — flag any symbol/digit absent from all example equations.
- The CoT is written in the **reasoner's voice** — no mention of solver/oracle.

Conceptual model enforced:
- **constrained symbols** = `content_symbols(examples)`. Only these have derivable
  digits; the entire digit-mapping derivation runs on these.
- **unconstrained question operands**: shown in the header marked `(unconstrained)`;
  their digit is a best guess at decode time.
- **answer-only symbols**: omitted from the header entirely; at encode time the
  reasoner computes result digits, and for each result digit not covered by any
  constrained symbol, the *symbol* is a best guess (digit→symbol direction).

### Fix

**A. `render_cot`**: added `constrained_syms = content_symbols(examples)`.
  - `compute_digit_priority` and `build_chain` now receive `constrained_syms`
    (not `examples + [q]`), restricting all derivation to example symbols.
  - The initial-reasoning call receives `_operand_symbol_display(examples, q)` (see B).

**B. New helper `_operand_symbol_display(examples, q)`**: returns constrained
  symbols in first-appearance order, followed by question-operand symbols absent
  from examples suffixed ` (unconstrained)`. Answer-only symbols omitted.

**C. Reworked `_answer_working`** — arithmetic branch only:
  - **decode line** via `_decode_display(s0, s1, solution, base, mode, known)`:
    shows `unknown` for unconstrained operand symbols; partial place-value
    (`unknown 6` for LE) when one symbol is unconstrained.
  - **guess line**: for each unique unconstrained question-operand symbol, emits
    `- unknown digit for symbol(s) \`|\`. Making a best guess: \`|\` = 4`.
    Omitted when all operand symbols are constrained.
  - **apply line** via `_apply_formula_str(fam, off, L, R)`: shows the formula
    with values substituted (e.g. `|16 - 46|` for absdiff) instead of the bare
    numeric result. This makes the derivation step transparent.
  - **encode line**: drops the `-> {symbols}` mapping at the end; appends
    ` (preserve the zero padding)` when `0` is in the display digit list.
  - **note line** via `_unknown_result_digits_note(digits_display, solution, known)`:
    for each unique result digit not assigned to a known symbol, guesses its
    symbol via the inverse map — in the **digit→symbol direction**:
    `- note: result digit(s) 0, 3 never appear in any example equation, so their
    symbols cannot be deduced from the examples. Making a best guess: 0 = \`@\`, 3 = \`'\``.
    Omitted when all result digits are covered by known symbols.

`predict_answer` / `decode.py` is **unchanged** — the `\box{...}` answer stays correct.
The concat path and per-step `\boxed{}` candidates are **not** affected.

### Sample output (arithmetic conclusion, unconstrained operand + answer-only symbols)

```
Using the feasible mappings to answer the question &:-&| (`little_endian`):
- decode: &: -> 6,1 -> 16; &| -> 6,unknown -> unknown 6
- unknown digit for symbol(s) `|`. Making a best guess: `|` = 4
- apply: absdiff(16, 46) (offset 0) = |16 - 46|
```
